# 课题概览

## 研究定位

硕士学位论文围绕**探索性数据分析**与**预测性数据建模**两个任务展开，设置两个核心研究章节。两个章节各自具有完整的研究问题和独立实验，同时能建立从数据理解到预测建模的递进关系。

> 两个核心章节均已确定初版方法与实验方向，下一阶段以工程实现和实验验证为主。第二章主实验基准确定为 DSBench-Modeling 与 TabArena-Lite；具体任务范围与运行预算需进一步通过适配与成本预实验确定。

## 第一核心章节：面向探索性数据分析任务的智能体研究

**核心研究问题：如何通过多步交互式探索，获得可信、可复现的数据分析结果？**

研究智能体如何在有状态的 Notebook 环境中，围绕分析目标自主开展多步数据探索，根据中间执行结果调整分析过程，并形成正确、有证据支持且可复现的分析结果。

- **任务目标：** 理解已有数据，回答分析问题，发现有依据的数据规律。
- **核心产出：** 分析结论、支撑证据及可复现的 Notebook。
- **独立实验：** 围绕数据分析任务，评价分析正确性、任务完成情况、证据充分性和结果可复现性。

### 初版方法：持久化 Notebook 与规划—执行分离

构建**基于持久化 Notebook 执行环境与规划—执行分离的探索性数据分析智能体**。内部设置规划智能体与执行智能体，对外作为一个完整的探索性数据分析智能体提供服务。

| 组成部分 | 职责 | 主要使用的信息 |
| --- | --- | --- |
| 规划智能体 | 判断分析方向，根据已有结果确定下一步需要获取的信息，向执行智能体下达分析任务，并判断何时形成最终结论 | 用户目标、数据描述、已有分析任务与结果、必要的失败诊断 |
| 执行智能体 | 操作 Notebook 内核，编写和执行代码，处理数据，获取并返回规划者需要的结果 | 当前分析任务、必要的统计口径与约束、相关代码、内核状态与执行反馈 |
| 持久化 Notebook 内核 | 保存跨步骤的数据、变量与中间计算结果，支持增量执行，并记录代码和执行产物 | 当前任务会话中的执行状态与单元记录 |

基本工作流程为：规划者提出分析需求 → 执行者编写并执行 Notebook 单元 → 返回分析结果与必要说明 → 规划者判断下一步探索方向或完成分析。该过程可以多轮迭代。

规划者不接收完整代码和逐次调试历史，主要围绕分析目标与已有证据推进任务。执行者返回的结果应包含理解结果所需的统计口径、样本范围、必要的数据处理说明、异常或局限，以及对应执行产物的引用；不能仅返回缺少含义说明的数值。

**不设置独立 Debugger。** 根据当前实测，代码报错率较低，暂时没有引入专门调试角色的必要。执行者在发生错误时依据执行反馈自行修复，并设置必要的重试上限。涉及分析口径变更、任务歧义或无法完成的情况，向规划者返回必要诊断，由规划者决定后续处理。

### 研究贡献与待验证假设

采用已有技术融合的研究路线，重点在于面向探索性数据分析任务的方法组织、工程实现与实证验证，不将 Notebook 内核或规划—执行分离本身表述为首次提出的技术。

- **规划—执行分离：** 检验将分析决策与实现过程分开，是否能够改善分析质量，或减少无关实现历史带来的上下文消耗。
- **持久化与增量执行：** 检验跨步骤复用数据和中间状态，是否能够减少重复代码、重复计算与 token 消耗，并改善任务完成情况。
- **完整系统：** 检验两项设计结合后的任务表现与资源开销，明确收益及适用范围。

这些是待实验检验的假设，不预设每项设计都必然提高分数。若某项设计主要体现为成本降低，或仅在复杂任务中有效，应据实报告；若没有稳定收益，则调整设计或缩小贡献表述。

### 主实验：与现有方案比较

使用数据分析任务的公开 Benchmark，以官方评分和 token 消耗为主要比较指标。具体 Benchmark、底层模型及基线实现后续选择，优先保证代表性和可复现性。

| 基线类别 | 比较目的 | 公平性要求 |
| --- | --- | --- |
| 纯 LLM 方案 | 评价工具调用与交互执行在所选任务中的价值 | 明确其能够访问的数据内容、摘要或截断规则；区分数据访问受限与推理能力不足 |
| 基础 ReAct 方案 | 评价任务专用设计相较于通用智能体执行循环的提升 | 尽量使用相同底层模型，明确工具、运行环境与预算差异 |
| 已有 Data Agent 研究 | 评价完整系统相较于现有数据分析智能体的表现 | 优先在统一设置下复现；引用论文原始分数时，与自行复现结果分开列示 |

既有研究的比较范围可从前期调研的 DatawiseAgent、TaskWeaver、DS-STAR 等方案中选择，最终名单根据任务适配性与复现条件确定。

纯 LLM 对比用于说明所选任务设置下工具执行的价值，不据此泛化为所有任务中 Agent 都优于纯 LLM。

### 消融实验：检验两项核心设计

| 版本 | 规划与执行组织 | 执行环境 | 目的 |
| --- | --- | --- | --- |
| 完整方案 | 规划者与执行者分离 | 持久化 Notebook 内核 | 作为完整方法的参照 |
| 消融一 | 一个 Agent 同时负责规划与执行 | 持久化 Notebook 内核 | 检验规划—执行分离的作用 |
| 消融二 | 规划者与执行者分离 | 每轮重新编写完整 Python 脚本，在新进程中从头执行 | 检验持久化状态与增量执行的作用 |
| 可选补充消融 | 一个 Agent 同时负责规划与执行 | 每轮重新编写完整 Python 脚本，在新进程中从头执行 | 构成四组对照，进一步观察两项设计的配合效果 |

**“去掉 Notebook”的定义：执行智能体每轮都相当于从头重新写代码。** 每轮生成能够完成当前分析任务的完整 Python 脚本，在新的 Python 进程中执行；不保留上一轮进程中的变量、已加载数据或中间计算状态。当前计算所需的数据读取、处理和前置计算需要在脚本中重新完成。该设置不等同于在常驻 Python 进程中继续执行代码。

脚本方案仍可保留任务与历史反馈上下文，因此消融主要检验执行状态的持久化与增量代码执行，而不是同时移除智能体的任务记忆。中间文件是否允许复用及其规则须在正式实验中统一说明，避免额外的数据访问限制混入比较。各组使用相同的数据、依赖库和必要的结果反馈能力，并尽量统一底层模型与资源预算。

### 指标与实验记录

- **主要指标：** Benchmark 官方分数；所有 Agent 合计的输入、输出 token 消耗。
- **辅助指标：** 总运行时间、任务失败率；必要时分析重复计算、代码修复与统计口径变化等失败案例。
- **记录要求：** 保存任务配置、模型版本、提示词、工具调用、代码与执行反馈、各角色 token 用量及最终答案，支持复现和问题定位。
- **稳定性要求：** 对存在随机性的结果进行必要的重复运行，不将单次运行中的微小差异直接视为稳定提升。

评分提高、成本降低以及质量与成本之间的取舍均应报告。规划者上下文减少不等于系统总 token 消耗减少，成本统计必须覆盖全部角色。

### 工程封装与下一阶段重点

对外将本章系统封装成统一的探索性数据分析智能体，隐藏内部角色分工与 Notebook 操作细节，供用户直接使用，也供第二章建模智能体按需调用。

- **输入：** 数据位置、分析目标、必要约束和执行预算。
- **输出：** 分析结论、支持结论的统计结果或图表、必要的数据处理说明，以及可追溯、可复现的 Notebook 与执行产物。

下一阶段优先实现统一执行接口、可靠的 Notebook 状态管理、规划与执行通信、完整轨迹及成本记录、可复现评测流程。暂不继续增加角色或额外机制，先完成初版系统并验证上述核心设计。

## 第二核心章节：面向预测性数据建模的智能体研究

**核心研究问题：如何通过自主机器学习实验，获得有效、可靠且高效的预测模型？**

研究智能体如何围绕预测目标，自主构建、评估和迭代机器学习流水线，在给定资源条件下获得具有良好泛化性能的预测模型。

- **任务目标：** 从数据中学习预测规律，获得对未见样本有效的模型。
- **核心产出：** 可复现的建模流水线、预测模型及独立测试结果。
- **独立实验：** 围绕预测建模任务，评价预测性能、建模成功率、资源消耗和结果稳定性。

### 初版方法：数据诊断驱动、预算约束下的自主建模

研究**面向预算约束的分析与建模协同优化方法**，重点回答：如何在有限预算下协调数据分析与模型训练，让分析结果真正改善实验选择、减少无效训练？初版优先面向表格分类与回归。

建模智能体根据当前模型的不足提出候选实验，主动调用第一章的探索性数据分析智能体调查相关不确定性，再依据证据调整实验优先级和训练预算。第一章作为完整能力接入，承担真实的分析任务；不将“挂接一个 EDA 工具”本身视为充分贡献，也不要求每轮训练前都开展全面分析。

| 模块 | 职责 |
| --- | --- |
| 建模智能体 | 维护当前最佳模型与候选方案，提出改进假设，在分析、训练、确认和停止之间选择动作，分配预算 |
| 第一章 EDA 智能体 | 分析指定数据、验证预测或实验日志，独立完成受委派的多步探索，返回结论、证据、适用范围及执行产物 |
| 实验执行工具 | 执行建模代码，保存模型、验证预测、指标、耗时及错误 |
| 实验记录与评价模块 | 关联分析证据和训练实验，使用固定的评价协议比较候选，管理数据、模型和产物版本 |

实验执行、记录与评价主要由普通程序实现，不必分别增加 LLM 角色。初版使用小型候选列表、当前最佳方案和少量备选方案，不将 MCTS 设为必需组件；若后续实验发现局部搜索不足，再研究分支搜索。

### 分析与训练的迭代流程

1. **建立初始模型。** 理解任务、评价指标与预算，按需委派与字段含义、缺失、实体或时间结构有关的分析，落实基准规定的评价协议，训练一个有竞争力的初始模型，保存验证预测和日志。
2. **提出候选实验。** 围绕当前问题提出少量具体改进，例如目标变换、缺失处理、特征构造、模型选择或正则化调整；说明每个候选依赖的判断及现有证据。
3. **由候选反向生成分析请求。** 在调用 EDA 前，明确待比较的实验、尚不确定的问题、需要观察的证据，以及不同分析结果将如何改变后续动作，避免无目的地生成通用分析报告。
4. **依据证据安排训练。** 更新候选优先级，对有希望的方案先开展有限预算试验，再决定是否扩大投入；统计现象只用于指导选择，不直接当作改动有效的证明。
5. **用训练结果修正判断。** 分开记录观察到的现象、提出的解释、实际改动与验证结果。失败实验可降低某条路径的优先级，但不应直接否定原始观察，也不应因单次分析永久排除一类模型。
6. **确认并交付。** 预算将尽或继续探索收益有限时，保留资源确认最佳方案、完成最终训练并导出可复现流水线和预测结果。

基本循环为：**当前模型 → 候选改进与疑问 → 定向 EDA → 更新实验优先级 → 训练验证 → 更新模型与证据。**

例如，面对回归误差，可比较“调整目标处理”和“改进缺失值处理”两个候选，并委派 EDA 分析目标区间与缺失模式的误差贡献。调用前说明两类证据分别支持优先尝试什么；分析后仍需真实训练验证，不能仅凭相关性认定改动必然有效。

### 预算调度与证据管理

- 现有证据已足以支持某个候选时，直接训练；多个候选依赖不同的数据判断且分析相对便宜时，先调查。
- 当调查成本接近直接试验成本时，优先考虑直接试验；为最终训练与验证预留预算，避免资源全部耗于探索。
- 保留少量探索机会，避免误判导致过早排除潜在有效方案。具体阈值、预算比例与停止规则在开发任务上确定。
- 每条证据关联数据版本、划分、模型或预测版本及生成成本；复用前检查适用范围，模型相关的旧误差分析不能无条件用于新模型。
- 成本覆盖建模调用、EDA 内部所有角色调用、分析代码执行和模型训练，分别报告 token、时间与计算资源，不将减少训练次数等同于降低总成本。

### 候选研究贡献与相关工作边界

贡献重点为：**面向实验选择的分析任务生成、分析与训练间的预算调度、可追溯的证据—实验反馈机制**。目标是在相同预算下提高预测性能，或在相近性能下减少总开销；这些收益需由实验检验。

已有方法已覆盖代码搜索、流水线优化、诊断反馈和 EDA 调用。[AIDE](https://arxiv.org/abs/2502.13138)、[SELA](https://arxiv.org/abs/2410.17238)可作为搜索方法参照；[MLE-STAR](https://arxiv.org/abs/2506.15692)研究定向组件优化；[KompeteAI](https://arxiv.org/abs/2508.10177)已支持搜索中按需 EDA；[Gome](https://arxiv.org/abs/2603.01692)与 [MLToolBench](https://arxiv.org/abs/2609.36679)分别涉及诊断驱动更新和诊断工具使用学习。因此不声称首次通过 EDA 指导建模，重点比较本方案如何将分析结果落实为实验选择与资源分配。

### 主实验与消融实验

主实验比较同预算下的预测质量与总成本。基线包括传统 AutoML（如 AutoGluon）、通用建模 Agent，以及可复现的代表性建模研究（如 AIDE、SELA、MLE-STAR 或更接近的方法）。具体名单后续按任务适配性、复现成本与方法接近程度确定，不要求复现全部文献。

| 对照版本 | 用途 |
| --- | --- |
| 建模智能体不调用 EDA 子智能体，保留基本数据访问与建模工具 | 检验第一章分析能力的加入是否带来收益 |
| 开始时进行一次 EDA，后续仅进行训练优化 | 检验一次性报告是否足够 |
| 允许按需调用 EDA，但不要求显式关联证据与候选决策 | 检验普通工具接入与完整机制的差别 |
| 完整方案 | 检验候选驱动分析、决策关联与预算调度的联合效果 |
| 可选：保留定向分析，但移除自适应预算调度 | 单独分析预算调度的贡献 |

评价包括官方预测指标、任务完成率、同预算性能、达到预设性能所需成本，以及随预算变化的性能曲线。结合轨迹检查分析结果是否改变候选优先级、实际执行了哪些改动、后续效果如何；调用次数或文字中引用证据的次数不能单独证明分析有效。

各组尽量统一底层模型、可用建模库、硬件、数据划分和总预算。EDA、调参、特征选择只访问允许使用的训练数据与内部验证产物；测试标签及测试评分反馈与全部智能体隔离。确认实验收益时使用独立测试结果，不能以反复优化的内部验证分数替代泛化性能。

### Benchmark 选择与适配评估

以下为 2026-10-10 根据官方论文、仓库、任务元数据和数据准备代码完成的静态核查，尚未运行训练或完整基准。**已确定基准来源不等于已冻结全部任务清单与计算预算。**

| 基准 | 当前定位 | 对本方案的适用性 | 主要限制 |
| --- | --- | --- | --- |
| DSBench-Modeling | 已确定的主实验基准 | 检验任务理解、数据处理、模型构建到预测文件交付的完整流程 | 74 项任务包含文本与序列等任务，不能整体视为低成本常规表格预测 |
| TabArena-Lite | 已确定的主实验基准 | 检验表格分类/回归的预测质量和预算效率，适合与传统 AutoML 对比 | Lite 主要减少外层划分；仍有 51 个数据集，不能把完整评测视为一次轻量运行 |

#### DSBench-Modeling

官方包含 74 项 Kaggle 建模任务，重新划分原始有标签数据进行本地评价，提供任务完成率与 RPG 等指标；适合检验端到端自主建模。其论文采用 8:2 训练/测试划分，实际运行应固定发布数据与脚本版本，内部验证集从可用训练部分产生。[论文](https://arxiv.org/html/2409.07703)

当前发布的任务清单既有 Titanic、Spaceship Titanic 等表格任务，也有文本建模、时间序列和特殊结构预测；CSV 文件格式不能作为表格分类/回归的唯一判定依据。主实验基准保留 DSBench-Modeling，但实施前须审计任务类型和大小；若仅采用常规表格部分，应明确命名为其表格子集，公开纳入与排除清单，不能报告为完整 74 项结果。[官方任务清单](https://github.com/LiqiangJing/DSBench/blob/main/data_modeling/data.json)

官方提供预处理后的建模数据压缩包，页面标示约 3.13 GB；这是下载体积，不能据此推断解压内存或训练耗时。先检查发布包再考虑逐项 Kaggle 下载，避免无必要地获取原始比赛全部文件。[下载说明](https://github.com/LiqiangJing/DSBench/blob/main/data_modeling/readme.md)、[数据包](https://huggingface.co/datasets/liqiang888/DSBench/blob/main/data_modeling/data.zip)

RPG 按官方实现为 `max(0, (score - baseline) / (reference - baseline))` 后进行任务汇总，**越高越好**；缺失或无效结果的处理也应遵循固定规则，不只统计成功任务。保留逐任务原始指标、参考分数来源与聚合配置，避免将 RPG 名称误解为越小越好的误差。[官方聚合代码](https://github.com/LiqiangJing/DSBench/blob/main/data_modeling/show_result.py)

#### TabArena-Lite

以 TabArena-v0.1 的 Lite 设置为初始目标：51 个经过整理的 IID 表格数据集，每个使用一个外层划分，覆盖分类与回归。其作用是检验受控条件下的建模质量与效率；它不能单独覆盖复杂任务说明、多表关系、时间依赖等全部能力。与 DSBench-Modeling 的完整任务流程形成互补。[TabArena 论文，尤其附录 A.4](https://arxiv.org/html/2506.16791)

**将本方法作为自主管理流水线的 system 接入。** 当前官方仓库区分 model 与 system，后者允许在给定预算内自行组织预处理、验证、搜索和集成，适合我们的建模智能体。不要给完整 Agent 再套一层面向单模型的 200 配置 HPO。保留官方外层测试划分，具体内部验证遵循所固定版本的 system 接口并明确报告。[官方集成说明](https://github.com/autogluon/tabarena#contributing-a-model-or-system)、[system 示例](https://github.com/autogluon/tabarena/blob/main/examples/benchmarking/run_quickstart_tabarena_system.py)

Lite 不自动取消内层训练开销。原论文的单模型协议使用内层交叉验证与配置搜索；system 的实际开销取决于自身策略和总预算。主对比应重新运行同硬件、同预算的基线；官方缓存排行榜可作参考，不直接据此宣称成本优势。开发阶段可选少量任务调试，正式只跑部分数据集时须标为 Lite 的子集。冻结版本、任务 ID、外层划分及评价配置，防止 living benchmark 后续更新改变实验定义。

该基准的数据已经经过整理，不能假定通用缺失值检查一定产生优势；更应检验模型误差、特征处理与候选训练选择等针对性分析是否有效。这是对本方法研究假设的实际检验，而非预设 EDA 必然有帮助。

### 本地数据准备

基准选择与评分说明已同步至 [benchmark.md](benchmark.md)，数据统一放在项目根目录 [benchmarks](../benchmarks/README.md)。2026-10-10 的下载候选包括第一章三套基准、DSBench-Modeling 的 52 项结构化表格任务、TabArena-Lite v0.1 的 51 个数据集。具体排除理由、版本和实际下载状态以该目录清单为准；候选集仍需经过成本预实验，不能将下载完成等同于正式实验集合已冻结。

### 成本预实验与实施顺序

1. 固定两个主基准的版本与任务元数据，核对任务模态、文件大小、训练样本数、评价指标、已知问题和数据来源重叠。
2. 在少量开发任务上运行一个树模型基线及最小建模循环，测量数据准备、训练、EDA、LLM 调用各自的成本；不根据本方法的测试分数挑选正式任务。
3. 据实设定单任务总预算、单次训练上限与重试上限。可先试较短预算档位，再决定是否需要延长；目前不承诺某项任务一定在若干分钟内完成。
4. 完成 DSBench-Modeling 与 TabArena-Lite 的适配、主对比和核心消融。

总实验量按“任务数 × 方法/消融数 × 重复次数 × 单任务预算”估算，另计数据准备与缓存开销。即使单任务轻量，全套多组重复运行仍可能累积数百小时；应先制定总预算，再决定任务范围与重复策略。最终交付模型、可复现训练/预测入口、验证预测、实验与分析轨迹及成本记录。

## 两个章节的关联与递进

两章通过**探索分析能力的按需调用与任务委派**建立关联。第一章研究能够独立完成探索性数据分析任务的智能体；第二章研究预测性数据建模智能体，并将第一章的探索性数据分析智能体作为可按需调用的工具，用于解决建模过程中遇到的数据分析问题。

预测建模智能体根据当前任务和实验进展，判断是否需要开展数据探索，并向探索性数据分析智能体委派具体的分析任务。例如，在构建模型前，可以委派数据分布与缺失情况分析；在模型迭代过程中，也可以根据实验反馈，委派针对特定特征或样本群体的进一步分析。探索性数据分析智能体自主完成相应探索并返回结论与证据，由预测建模智能体据此继续进行建模决策、训练和验证。

这种协作不要求预先完成一次全面探索，也不将一份固定的分析报告设为建模的必需输入。探索任务可以在建模前或迭代过程中按需发起，调用次数和分析范围由实际任务需要决定。

两章的递进体现在：**第一章建立可独立使用的探索性数据分析能力，第二章在自主机器学习实验中按需调用该能力，完成预测建模目标。** 第一章自身具有完整的分析任务与研究价值；第二章则围绕建模任务开展独立研究，探索能力的调用是其完成任务的一种支撑。
