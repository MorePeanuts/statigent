# Design

## Context

动机与范围见 [proposal.md](proposal.md)，研究依据为 `docs/overview.md` 第一章。当前 `src/agent/run.ts` 将模型请求、预算、动作校验、执行和收尾放在一个循环中，`AgentSession` 已提供可替换的执行接口。`DockerSession` 已实现任务隔离、串行执行、取消和持久状态，无需另建内核层。

现有任务只选择一个模型；`agent/prompt.ts`、`actions.ts` 只支持 `execute_python` 与 `finish_analysis`。报告由执行代码保存，再经 `resolveReport` 校验。运行清单 v2 只有一套模型/提示词和用量；评测契约 v2 已支持文本、报告及冻结交付，但 Statigent 适配器固定 `single`，且只透传模型次数、token 与时限，代码次数仍落到默认 8 次。

本次跨编排、记录和适配模块，且改变报告作者与产物来源，需要在实现前明确协议、兼容路径与验收边界。

## Goals / Non-Goals

**Goals:**

- 用一个宿主编排器、一份全局账本、一个隔离会话支撑双角色协作；统一外部任务与分析结果，不向调用者暴露角色调度细节。
- 信息流边界由代码保证，适中粒度由提示词引导。完整日志与角色消息历史分离，记录完整不意味着每个角色都读取完整历史。
- 可用可控响应验证委派往返、跨委派状态、角色可见内容、总预算和真实交付，不依赖随机文本匹配。

**Non-Goals:**

- 不增加通用多智能体框架、并行执行者、递归委派或独立摘要/调试角色。
- 不做语义粒度分类、动态粒度策略、自动上下文压缩和基于评委反馈的分析修正。
- 不在本次确定正式实验预算或开展第二章建模；完整范围排除项见 proposal。

## Decisions

### 1. 同一 EDA 入口显式选择组织方式

任务新增 `organization: single | planner-executor`，缺省保持 `single`。执行后端仍为持久内核；不接受尚未实现的新脚本模式。第一版两个角色使用调用方选择的同一个模型 profile，各自拥有独立消息历史及提示词版本，CLI 的 `--model` 同时作用于两者。不同角色使用不同模型留待独立需求，不引入评测模型控制歧义。

保留 `runAgent` 的统一返回语义。提取模型调用、记账、记录、执行反馈与收尾的共用部分；单角色与双角色仅在工具集合、消息路由和状态转移上不同。不通过递归调用当前 `runAgent` 启动执行者，否则会重建容器、复制预算并割裂证据。

### 2. 宿主串行路由，两个角色各有工具权限

```text
Caller --> EDA host --> Planner
                         |
                  delegate_analysis
                         v
                      Executor --> execute_python --> Persistent kernel
                         ^                                |
                         +----------- feedback -----------+
                         |
                    return_result
                         v
                      Planner --> delegate again / finish_analysis
                                                    |
                                              Host validation
                                                    |
                                                 Delivery
```

规划者工具为 `delegate_analysis` 和 `finish_analysis`；执行者工具为 `execute_python` 和 `return_result`。每次模型响应仍只允许一个动作；越权、多动作和非法参数按现有动作纠正规则处理。执行者不能完成整个 EDA，也不能反向调用规划者工具。

宿主接受委派后生成唯一 `subtask_id`，先记录委派，再唤起执行者；在执行者有效返回之前不再次调用规划者。有效返回作为原 `delegate_analysis` 的 tool result，规划者下一次模型请求自行判断继续或完成。执行者收到 `return_result` 接受回执后保持可续接的合法消息历史；下一次委派以新消息进入同一历史，避免悬空 tool call。

### 3. 协议保持简洁，粒度写在提示词中

委派参数为 `task`（非空问题描述）和 `constraints`（可为空的约束列表），不要求模型填写复杂计划、步骤树或粒度标签。宿主附加子任务身份、当前全局剩余预算和允许输入说明；全局权限与用户约束不能被委派覆盖。

执行者返回：

- `subtask_id`：回传宿主提供的当前子任务身份，拒绝错配或重复终结；
- `status`：`completed | partial | needs_clarification | failed`，只描述当前子任务；
- `summary`、`findings`（statement、可选 value、evidence_refs）、`methods`、`limitations`；
- `diagnostic`：有界的必要诊断，无须错误栈；非完成状态必须说明阻塞或未完成原因。

`completed` 必须有带有效证据的结果及统计口径；其他状态允许无 finding，不能伪造证据。可复用前一子任务的本任务证据，不要求每次委派都重新执行。宿主验证引用确实属于当前运行、已成功单元或完整执行产物；返回中引用的图片附加受限描述符（产物 ID、类型、可用相对引用），供规划者最终报告使用。

规划者提示词以“一个明确、结果能够支持下一步判断的分析问题”为默认委派单位，并给出粗、适中、过细的例子。执行者提示词允许为回答该问题检查数据和多步求解，遇到新分析方向返回线索，不无限扩展。提示词内容和版本进入运行记录。代码只验证结构、引用、权限和额度，不通过关键词、额外 LLM 或硬编码任务数评价粒度。

### 4. 独立上下文与连续内核

规划者获得总目标、用户约束、允许输入描述、自己的委派与已接受结果。宿主不向其拼接执行代码、原始工具反馈、错误栈、执行者模型响应或推理字段。执行者获得总目标及约束、每次具体委派、自身历史和执行反馈，不获得规划者完整推理历史。

每个 EDA 任务只有一个执行者历史和一个 Docker 会话，所有委派共用变量与工作文件；任务间完全隔离。执行者负责核对复用状态的口径。第一版保留两个角色各自的完整历史，分别检查请求大小，共用总轨迹上限；不自动摘要、丢弃旧消息或重启内核。

首轮真实验收暴露了“保留状态但未引导模型使用状态”的缺口。角色提示词 v2 明确以当前委派为执行范围，总目标仅作背景；执行者仅获得图表产物限制，不获得作为自身交付要求的完整报告契约。规划者负责报告和依赖前序证据的后续决策，不默认通过 CSV 文件交接同一内核中的状态。宿主每次委派附 `execution_context`：持久后端、是否延续先前委派、前序委派数和已开始执行次数，均来自当前运行。执行者先依据历史核对内存状态，默认复用适用变量、增量执行；确有状态缺失、口径变化或独立核验需求时可重新加载/重算，在代码注释及 methods 说明原因。此为提示词行为约定，不增设代码关键词禁令、变量管理服务或语义校验器。

结构化返回中的自由文本仍由模型撰写，提示词要求只总结结果及必要诊断；代码可保证不自动注入原始调试历史，但不能保证模型自由文本绝不复述代码。验收分别检查实际消息路由与真实冒烟内容，不声称已解决语义信息过滤问题。

### 5. 共享预算；子任务状态与全任务状态分离

复用现有 `AgentBudget`。模型次数、token、任务时限、执行次数和轨迹配额覆盖整个任务，切换角色或委派不重置。限流重试及动作纠正消耗全任务对应额度；连续代码错误计数仍在成功执行后重置，不能靠新委派清零。派发和响应结算遵循已有未知用量、token 阈值与取消规则。

第一版不增加每个子任务独立预算或自适应分配器：执行者可主动返回 partial/needs_clarification/failed，由规划者在剩余全局额度内决定下一步。真实代码修复额度耗尽、内核丢失、记录不完整或未知用量仍是全任务终止，不允许包装成可恢复子任务结果继续调用。

代码次数达到上限后，仍可在剩余模型预算内调用 `return_result` 和 `finish_analysis`，但不得再执行代码；模型次数、token 或总时限耗尽则不允许额外 LLM 总结。拒绝执行后按既有终态规则退出，不自动补写答案。宿主可保存已有结构化结果并标未完成。取消通过一个根信号传递给当前模型请求/执行，所有迟到响应都不得触发新动作。

每次执行反馈、子任务返回反馈和新委派均附宿主计算的剩余额度，使当前角色能够在执行次数用完时选择返回或完成；额度不由模型自报告。首版不预先固定规划者/执行者 token 比例。

评测适配器新增 `options.organization` 与 `options.budget`。后者仅允许 `AgentBudget` 中未由统一评测掌握的执行次数、修复/纠正/限流重试、单请求时限及请求/响应/轨迹大小字段；禁止覆盖模型尝试次数、总 token、任务时限，这三项以评测单元实际剩余预算为准。缺省沿用原默认值，生效预算完整进入预检与运行记录；不在通用评测 Budget 中加入 EDA 专属字段。

### 6. 规划者提交结论，宿主保存报告

单智能体保留现有完成 schema 和执行者保存报告的路径。双角色的 `finish_analysis` 复用现有 summary/findings/methods/limitations；报告任务另要求 `report_markdown`。规划者只能引用已通过子任务结果返回给它的证据，不能猜测其他有效但未见过的 ID；至少一次成功执行及有效 finding 仍是全任务完成前提。

执行者生成图表并在结果中引用。宿主给规划者提供稳定的交付相对路径，例如 `images/<artifact_id>.png`，绑定到指定产物快照，后续工作区同名文件变化不改变此引用。规划者将其写入 Markdown；宿主校验路径、图片格式、数量、大小和已返回证据范围，拒绝外部链接、虚构及跨运行图片。

校验全部通过后，宿主将规划者原文保存为报告产物并生成现有 `AnalysisReport` 映射，适配器继续交付报告和引用图片。宿主不改写分析结论，也不额外调用执行者转存 Markdown。新增受限宿主报告保存能力，记录来源是规划者最终调用，而非伪造 Python 单元；写入失败不能返回 completed。无效报告在落入最终交付前拒绝并计入纠正预算。

报告保存同时遵守报告大小与原生产物配额，预检明确生效限制；图片别名与宿主报告路径属于交付命名，不冒充执行工作区实际路径。扩展产物来源及解析时保留旧 source_path 语义。

Notebook 仍只包含实际执行单元；代码重放不调用规划者，因此不重新生成宿主保存的最终报告，也不声称验证了报告语义。这一边界在 inspect、使用说明与验收中说明。

### 7. 原生记录演进，评测保持现有交付协议

为双角色引入原生运行清单 v3，原单角色和 runtime 继续按既有 v2 写入；v1/v2 不原地迁移。v3 保留通用运行/会话/产物与顶层总用量，模型和提示词按 planner/executor 记录；为两个角色提供用量小计，并校验与总账一致。两个角色即便使用相同 profile，也保留各自返回模型身份、请求与提示词哈希。

模型尝试和相关事件增加 role、可为空的 subtask_id；委派、结果返回及最终提交有独立事件，关联工具 ID、执行请求、单元、产物及接受状态。无 subtask_id 的规划者请求仍计入总预算；子任务用量以执行者实际尝试为口径，不与角色小计重复相加。请求意图先落盘，未完成请求保持未知。

更新记录检查、inspect、Notebook 导出、代码重放和评测用量提取，使用版本分支归一化，不靠类型断言假装兼容。报告产物标明 planner 来源，不赋予不存在的 cell_id；完整执行及模型轨迹仍在宿主独立保存。

评测契约维持 v2，适配器版本升级并记录 organization、persistent-kernel、角色提示词和实际预算。统一轨迹继续按实际单元顺序给出代码、输出摘要与最终报告，增加映射版本说明 executor 提供代码、planner 提供最终报告；不将完整角色推理和宿主路径混入评分交付。旧批次及旧映射继续可读、可重评，不重新运行智能体。

### 8. 以协作行为验收，不要求正式基准收益

可控模型测试强制覆盖至少两次委派：第一项加载并生成中间结果，第二项复用变量，最终由规划者引用证据完成。检查实际请求体，确认规划者未收到原始代码/调试历史，执行者历史和内核连续；拒绝越权工具、伪造结果身份及未返回给规划者的证据。

Docker 集成覆盖真实变量复用、报告与图表交付、独立任务隔离、取消清理及 Notebook 重放；额外覆盖带原始错误的轨迹按既有规则不支持严格重放。用无付费的评测测试验证两种组织方式均映射到原生结果和总成本。

提供显式双角色真实模型合成冒烟入口，任务包含可核验统计、图表及依赖前序结果的后续分析；工具协议不强制委派次数，验收器检查实际轨迹是否出现至少两次有效委派及跨委派复用。未观察到则如实报告该项未通过，不追加尝试直到成功。实施验收记录全部尝试、两角色用量、终态和产物；正式研究收益及基准比较另行开展。

## Risks / Trade-offs

- [适中粒度仍可能漂移] → 版本化提示词、检查实际委派轨迹；不把提示词引导表述为程序保证，后续按证据决定是否研究粒度。
- [返回结果遗漏重要口径] → 要求 methods/limitations 与可追溯证据，允许规划者再委派；引用存在不等于语义正确。
- [执行者长历史及角色往返增加成本] → 有界请求和总预算、按角色实测；不预设双角色更省 token。
- [报告转为宿主保存改变来源语义] → v3 明确模型作者和产物来源，Notebook/报告复现状态分别说明；单角色旧路径不变。
- [提取公共循环破坏原行为] → 分阶段保留旧单角色测试，再新增角色路由覆盖，不能复制两套预算/失败处理代码。

## Migration Plan

1. 先实现并验证公共调用/预算基础和 v3 读写兼容；所有旧配置仍走 single。
2. 增加双角色协议、提示词、编排与最终交付，使用独立示例配置显式启用。
3. 扩展适配器预检、预算映射、轨迹和文档，完成快速及 Docker 集成检查，再经显式入口做有界真实冒烟。
4. 若双角色暂不稳定，调用方选择 single 即可继续使用原流程；保留失败的 v3 运行，不覆盖为 v2 或删除记录。旧版本程序不保证读取 v3，新版本必须兼容旧记录。
