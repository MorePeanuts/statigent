# Design

## Context

动机与用户确认范围见 [proposal.md](proposal.md)。研究依据为 [overview.md](../../../docs/overview.md)，当前主线合并提交为 `72c83a3`。下表来自本次只读核查，不表示相应改动已经实现。

| 当前位置 | 观察到的行为 | 对本设计的影响 |
| --- | --- | --- |
| `src/modeling/actions.ts` | 三个工具；`analyze` 必须有候选、决策规则和三项额度；提示词要求先训练 | 升级动作与提示，允许分析先于候选和初始训练 |
| `run.ts` | `pendingAnalysis` 强制下一次训练引用最新分析；仅保留候选摘要与追加聊天历史 | 移除此硬约束，增加独立认识状态和明确上下文视图 |
| `candidates.ts` | 候选与实验身份分离，优先级不强制调度，更新有版本 | 保留此基础，增加认识引用，不另建搜索树 |
| `eda.ts` | 数据分析可无来源实验，但只能发布一个实验的预测；给子任务限定“当前候选疑问” | 支持探索、诊断、对比和跨轮认识交接；复用完整第一章 EDA |
| `budget.ts`、`config.ts` | 子额度依赖模型申请；默认一次 EDA、三次搜索拟合；总账与交付预留已有实现 | 改为宿主确定子额度，保留统一账本，显式选择新方法资源配置 |
| `experiments.ts`、`data.ts` | 单个冻结内部划分，`final` 布尔区分搜索与交付 | 增加确认阶段与评价身份，原始数据清单不改写 |
| `records.ts`、`delivery.ts` | 父/交付 schema 1/2；检查重演协议 2 的候选更新、额度与最佳选择 | 新记录版本独立解析，扩展离线审计与交付选择依据 |
| `smoke.ts`、分类冒烟与配置 | 固定流程验收，部分逻辑绑定动作协议 2；没有四组方法入口 | 保留历史结论，新增方法验收配置，测试控制流程与研究效果分开 |

当前初始模型上下文只有任务协议、字段名、行数和资源限制，没有统一的字段统计概览。直接去掉 EDA 会混入信息可见性的差别。当前可用模型库也限定在已锁定环境，本变更不同时增加建模库，以免把库扩展与协同机制收益混为一谈。

## Goals / Non-Goals

**Goals:**

- 实现可运行的双向协同：分析产生候选，模型表现产生分析问题，实验反馈修正认识。
- 明确模型判断与宿主事实的边界，允许拒绝某条分析建议而继续建模。
- 以共享底座提供四组对照、终局确认与完整成本记录，支撑后续效果实验。
- 逐阶段可独立验收和提交，旧数据、运行与交付保持可读取、复现和评分。

**Non-Goals:**

- 不引入长期知识库、向量数据库、自动知识图谱、MCTS、新固定 LLM 角色或通用工作流框架。
- 不提供任意更换验证集、在线查看外层测试、隐式恢复任务或跨任务共享状态。
- 不在本次实现完整 Benchmark、传统 AutoML 基线或正式实验调度平台；当前表格任务类型、指标、模型库与数据大小边界保留。

## Decisions

### 1. 以显式方法配置选择新运行语义

新任务使用配置 schema 2，必须声明 `method`，取值为 `no_eda | initial_eda | adaptive_eda | collaborative`。方法决定提示词与工具可用性；宿主也校验模式约束，不能只靠提示词。缺少新版本或方法的旧任务文件在新 `run` 入口预检给出迁移指引；历史 `inspect/reproduce/score` 不经新任务启动校验，继续按冻结旧配置解释。

这是有意的启动配置变更：不长期维护两个在线循环，也不把已有未标记配置静默认作新方法。仓库可执行示例与测试夹具随实现迁移，历史运行目录不迁移。资源配置与 `method` 分离，同一组任务进行消融时使用同一资源配置，不能为完整方法偷偷加额度。

### 2. 所有组先获得相同的基础数据概览

新增 `profile.ts` 与可信 Python 概览入口。只处理现有内部训练成员，输出行列数、解析类型、缺失/唯一值数量、数值分位数、类别频数与训练目标概要；不做特征相关性排名、误差诊断或自动建模建议。类别频数限制条数，字符串截断，明确缺失口径、解析失败及截断数量；不自动将 ID 加入特征，也不更改类别或拟合预处理。

Python 通过 `uv`、结构化消息和明确超时执行；它是可信固定计算，不执行模型生成代码。概览绑定输入、训练成员、协议与生成器版本，保存完整有界 JSON 与提示摘要；大表的字节/列数限制沿用并显式诊断。全部方法获得同一概览，耗时纳入本任务，不增加付费模型调用。训练工具仍可访问允许的拟合数据，各组不因消融改变训练能力。

选择轻量固定统计而不免费运行一次完整 EDA：保证基本数据可见性，同时保留第一章能力本身作为对照变量。

### 3. 认识状态采用小型记录表，不将其变成知识平台

新增 `knowledge.ts`，保留 `CandidateState`。完整协同模式维护三类记录：

| 记录 | 内容 | 可更新的判断 |
| --- | --- | --- |
| `observation` | 有来源的数据现象或模型表现 | `active / withdrawn` |
| `hypothesis` | 对现象的解释、预期作用或建模假设 | `open / supported / challenged / withdrawn` |
| `question` | 尚需调查的问题 | `open / resolved / withdrawn` |

共同字段为稳定 ID、类型、陈述、状态、理由、引用、关联候选、修订号和前一修订。模型提交 `create/revise`，宿主分配版本和接受事件序号；数据/协议作用域由宿主绑定。修改保留旧陈述与理由，不覆盖历史。`supported` 是智能体基于记录作出的判断，不是统计显著性或因果认证。

来源为带类型的联合结构：基础概览路径、已完成 EDA finding、已确认实验事实。EDA 引用使用分析 ID、finding 序号、其原始执行证据和来源清单哈希；实验引用指向宿主计算的成绩或真实失败诊断，模型不能自填可信分数。观察必须有有效来源；假设和问题可以暂时没有来源，但须明确为待验证判断。将假设标记为受到实验支持时须引用成功实验；代码异常只支持执行失败这一事实，不自动反驳统计假设。

候选增加 `knowledge_refs`，保留现有候选 ID、改进方向、修复身份与实际实验关系。不按观察数量、引用数量或状态名称奖励模型。完整模式可提交空更新，简单任务不必为了格式制造认识记录；专项验收使用固定轨迹验证状态能被真正创建、修正并影响后续动作。

### 4. 保留三个主要动作，放开探索路径

动作协议升级为 3。三个主要工具仍为 `run_experiment`、`analyze`、`finish_modeling`，一次只接受一个动作。

| 动作 | 新语义 |
| --- | --- |
| `analyze` | `purpose: explore/diagnose/compare`、具体问题、希望理解的现象、可空候选列表、来源实验列表、可空认识引用；不接受额度申请字段，不强制预写所有可能结果的决策规则 |
| `run_experiment` | 候选、代码、具体改动、选择理由、来源/修复实验；完整模式可关联认识和真实 EDA 证据。无新分析时可直接训练 |
| `finish_modeling` | 提交主动完成理由和当前搜索最佳实验 ID，宿主验证后冻结搜索并执行配置的确认与交付；开启确认后，提交 ID 不等于保证最终选中 ID |

`explore` 无来源实验即可调用，候选列表可以为空；`diagnose` 必须引用一个成功的搜索实验；`compare` 必须引用两个不同、同搜索评价身份的成功实验。初版最多两个来源，避免引入任意多模型产物聚合。失败实验可作为事实诊断进入认识，但不能伪造残差或验证预测。

完整模式的 `knowledge_updates` 与 `candidate_updates` 随同动作原子接受；无效引用、陈旧修订、非法模式或额度不足时整个动作拒绝，不留部分状态。没有独立的“填写状态”必经动作。其他模式不暴露认识更新字段；候选和实验事实记录仍由同一底座维护。

取消 `pendingAnalysis` 强制引用。分析结果允许被采用、暂缓或不采用；在完整模式下通过选择理由与相关认识修订表达，不要求每次分析立刻训练，也不添加“必须逐条处理报告”的硬门槛。引用若存在则必须真实，不能通过删掉来源校验来放松流程。

### 5. 显式交接 EDA 上下文，保留会话隔离

扩展 `prepareAnalysisInput`：保留允许的训练数据与搜索划分；单模型诊断发布其验证表；对比诊断发布两份按稳定 ID 对齐的独立预测表与来源映射；纯探索不伪造实验身份。禁止交接外层测试、最终模型加载权限或完整宿主目录。

新增 `context.json`，包含本次问题、候选定义、指定认识的准确修订、原始来源及相关未解决问题。旧分析结论以“既有认识”标记，不改挂为本次执行证据；不同模型的残差证据仍分别绑定来源。子 EDA 返回结构沿用第一章 Analysis 契约，建模侧负责与状态关联，不要求修改第一章内部角色协议。

新 `prompt.ts` 构造模型可见状态：共同事实层为任务/协议、基础概览、搜索最佳、候选及实验摘要、资源余额；完整模式再增加认识表。保留建模自身的必要代码与反馈，EDA 内部代码和逐次调试不进入建模上下文。状态与分析上下文均有字节/条数上限，展示被省略条目的 ID/修订，不截断成看似完整的证据。显式引用的条目若放不下则在派发前报告上下文超限，不静默遗漏。

首版继续使用现有有界会话历史，不引入 LLM 摘要或语义检索；知识摘要按“动作引用、当前最佳相关、开放问题、最近修订”确定性排序。增长达到现有请求上限时如实停止或反馈，不宣称已解决无限长会话。

### 6. 宿主管理额度，配置区分冒烟与多轮开发

新 EDA 分配策略 `host-cap-v1` 对每一维采用 `min(配置子上限, 父剩余可用量)`；时间先扣除收尾预留。模型可见实际剩余资源和收尾提示，但不填写 token、毫秒或执行次数申请。低于一项正额度时拒绝派发，实际消耗按唯一子运行身份结算；token 继续是停止阈值而非精确费用封顶。

确认开启时，收尾预留覆盖最多短名单数 × 确认划分数的拟合尝试，以及最终拟合/预测；计入父总额度。预留次数与时间由配置明确声明并预检一致，不能临近结束无成本地追加确认。不要尝试自动预测“分析收益/单位成本”。

现有显式小额配置保留为开发冒烟资源档位，迁移方法字段后仍保持原额度。新增 `collaboration-dev-v1` 显式开发配置：允许至少两次 EDA、足够的搜索及收尾拟合，并通过 `--preflight` 展示生效总额、子上限、确认预留。其具体时间/token 数值由独立开发成本核对确定，未经显式选择不扩大旧入口调用成本，也不将该档位标为正式实验配置。

用量未知、记录失败、取消、容器异常的现有停止规则保留。无可派发探索动作时提示收尾，不反复让模型申请同一个不可能的动作。未明确接受 `finish_modeling` 或全任务资源已耗尽时，只保留现有产物及真实终态，不自动宣称自主收敛或最终交付成功。

### 7. 终局确认采用固定训练内重复留出

配置 `confirmation.mode = none | terminal_repeated_holdout`。`none` 用于最小冒烟；协同方法开发验收另提供开启确认的配置。四种方法的同条件比较必须使用同一确认模式与计划。

选择终局固定确认而非开放式 `confirm` 工具：确认不成为新的无限搜索渠道，所有组按相同规则完成最终选择。

具体流程如下：

1. 在首个模型请求前，从允许训练数据生成并保存两份额外 80/20 划分；回归沿用稳定 ID 哈希方法，分类沿用分层哈希方法。种子由任务种子和固定确认索引派生；精确成员、模型种子、生成算法与哈希写入 `validation-plan.json`。原搜索划分不变，旧 dataset schema 1/2 只读加载。
2. 开启确认但无法形成两个不同于搜索且彼此不同、两侧均覆盖冻结类别的合法划分时，在调用模型前拒绝并解释，不根据结果反复换种子或静默退回无确认。
3. `finish_modeling` 接受后冻结代码、搜索历史及短名单：按原搜索指标取前两份不同 `code_sha256` 的成功流水线；同代码只取其最好搜索实验，平局取先完成者。少于两份时按实际数量确认，并标记没有双方案比较。候选优先级及暂缓状态不从名单中排除已有高分成功流水线。
4. 两个额外划分对全部入选流水线各重新拟合并预测；候选内预处理每次只拟合该划分训练部分。使用相同评价与运行环境，不复用不同划分的模型或拟合变换。每次拟合和预测串行、独立、计账。
5. 以两份额外划分的主指标算术均值选择最终流水线，严格按指标方向；均值平局时保留搜索排名更高者。原搜索分数独立展示，不混入确认均值。展示逐划分值、均值及极差，不将两次结果称为统计显著或跨任务稳定收益。
6. 任何短名单流水线的规定确认试验失败或超时，整个确认不完整；保留全部诊断，不按剩余成功试验平均、不排除失败流水线后报完整确认、不退回未经确认交付。本版不在确认阶段改代码或请求模型修复；操作者可在开发中诊断后创建新运行。
7. 确认后不再调用建模或 EDA 模型，宿主按选择结果在全部允许训练数据上拟合并交付。最终拟合失败按现有规则如实记录，不把搜索模型冒充最终交付。

确认是**内部重采样检查与终局选择**。EDA 与特征设计可能已经使用过允许训练数据的标签，额外划分也存在样本重叠，因此不能称为未见过的独立 holdout，更不能替代冻结外层测试。该局限写入报告；将来若研究严格独立的内部确认集，需要另行定义数据可见性，不在此处假装已经实现。

实验记录增加 `phase: search/confirmation/final`、`evaluation_id`、来源搜索实验、划分哈希和模型种子。保留 `Score` 的指标语义身份，另用评价身份约束比较；最终拟合分数仍为 null。拆分 `search_best_experiment_id` 与 `selected_experiment_id`，避免确认改变选择后被旧检查器误认为篡改最佳分数。

### 8. 四种方法共用底座，明确消融含义

| 方法 | EDA 可用性 | 显式认识状态 | 训练/确认/交付 |
| --- | --- | --- | --- |
| `no_eda` | 不提供 EDA 工具，伪造调用被拒绝 | 不启用 | 共享 |
| `initial_eda` | 首次搜索拟合前固定一次探索，成功报告随后保留，之后禁用 EDA | 不启用 | 共享 |
| `adaptive_eda` | 按需探索、诊断、对比 | 不启用，保留正常报告与实验历史 | 共享 |
| `collaborative` | 同 adaptive，可空候选探索、多轮诊断 | 启用来源关联、修订和跨轮认识交接 | 共享 |

`initial_eda` 的一次初始委派由宿主生成固定的任务相关概览问题，计入同一总账；失败记为初始分析失败，仍可建模，但不得自动重做或把该运行称为完整分析链成功。其他模式不强制首次动作或 EDA 次数。四组使用相同模型、字段概览、可用库、数据划分、实验执行和确认规则；`no_eda` 未消费的 EDA 额度不虚扣，可以用于其余合法动作。

普通工具组的提示只定义工具和通用建模目标，不要求按三机制写认识状态；它仍能自然利用历史分析报告，不能故意清空记忆。完整组的差异包含显式认识管理、证据关联和相应决策提示的联合机制；这组消融不能单独归因于某个字段或提示词，报告中明确此边界。

### 9. 版本化记录与可审计交付

- 新父运行与交付 schema 3、动作协议 3、建模提示 `modeling-v4`，分别记录方法及资源配置版本；dataset schema 1/2 与现有 runner stage schema 保持原语义。
- 新分配记录 `allocation.version=2`、`policy=host-cap-v1`，记录配置上限、剩余量、收尾预留、实际分配与裁剪；不伪造不存在的模型申请。旧 allocation 继续由旧规则检查。
- `knowledge_control` 记录修订与接受事件；来源清单、数据概览、评价计划、候选短名单及实际模型可见快照均保存哈希。检查入口从已接受事件重建，拒绝快照与事件不一致。
- 搜索最佳、确认排名、最终所选、完成原因、交付状态和各阶段成本分列。普通模式的认识状态标为 disabled；旧记录标为 not_recorded。
- `reproduce` 对新交付只恢复已冻结的最终选择与模型；`--mode refit` 重训该流水线，不重新进行搜索或短名单选择。离线 score 不反馈智能体，旧 schema 1/2 与 EDA 记录继续按原版本读取。

### 10. 分阶段实施与文件职责

| 阶段 | 主要位置 | 独立可验收结果 |
| --- | --- | --- |
| A 协议与共同输入 | `config.ts`、`actions.ts`、新 `profile.ts`/Python 概览入口、版本读取 | 预检与概览在四组一致，旧记录读取不变 |

### 11. 验收分层与研究结论边界

1. 单元测试验证模式能力、认识来源与原子更新、额度、确认排序与失败、版本兼容；使用可控响应，不以 LLM 自然语言完全匹配为断言。
2. Docker 合成回归/二分类/多分类验证实际流水线、两次隔离 EDA、对比预测交接、固定划分、确认与预测复现；可以设计已知应改善的合成数据来检查实现，但不据此报告研究收益。
3. 提供新方法 `--preflight` 和独立真实模型入口。开发范围先沿用固定 s3e9 回归任务与已有分类合成任务；完整协同真实冒烟检查实际认识修订、跨轮分析和交付，不强制真实分数提升，不通过改题、丢弃失败或自动加跑取得成功。
4. 四组真实比较只在显式选择任务、模式、种子和资源后运行；输出逐任务成绩、终态与成本。报告明示开发性质、单次观察局限，正式基准收益仍待后续实验。

### 12. 真实冒烟后的可靠性修复

建模委派的 EDA 显式启用 `modeling-diagnostic-v1` 收尾策略，独立 EDA 默认不启用。限制单次生成长度，并根据当前两角色请求字节估计、返回内容余量、剩余调用/执行/时间，在硬上限前切换到只返回结果和总结的阶段；记录触发原因与数值。不删减执行者历史、不伪造总结、不将失败单元作为证据。提示要求优先诊断已有预测，新的候选拟合建议交回建模端。此策略是运行保护，不改变方法组定义或总资源档位。

新拟合使用版本 3 stage 配置声明压缩及产物上限，先压缩序列化，再检查大小；超限文件删除后抛出明确异常。宿主只有在执行回执完整、内核可用、清理和记录成功时把该错误识别为可修复的候选失败，并走已有搜索修复上限；保存和清理未知仍停止。确认阶段继续禁止改代码或按部分成绩交付。旧 stage 1/2 与旧模型加载保持兼容。

原失败记录不覆盖。用户已授权修复后再运行 s3e9 一次，沿用原模型、方法、种子及总额度，冻结新的代码和镜像；独立报告运行成功、完整协同验收与预测复现，不以任务复测执行完毕代替验收通过。

## Risks / Trade-offs

- [认识表成为格式负担] → 保留三种类型和少量状态，允许空更新，只有引用与来源实施硬校验；不要求按表演完所有步骤。
- [LLM 自信解释被当成证据] → 主张与宿主事实分列，观察必须有来源，supported 仅是判断，效果仍由真实实验评定。
- [记录和上下文膨胀] → 确定性有界摘要、完整历史另存、显式截断信息；首版不建设通用压缩系统。
- [额外确认成本与失败率上升] → 最多两份流水线、两个额外划分，明确收尾预留；失败如实报告，none 模式只用于声明不做确认的配置，各对照同条件。
- [训练内确认仍有自适应偏差] → 不宣称独立泛化评估，终局冻结后不再反馈搜索，外层测试保持完全隔离。
- [新机制在现有模型库上未见稳定提升] → 本次先证明行为可运行，后续开发比较据实调整；模型库扩展单独研究并对各组统一。
- [多版本分支破坏历史审计] → 保留旧解析与选择规则的只读路径，新格式缺字段拒绝，不猜测新字段；以原运行文件哈希核验不变。

## Migration Plan

1. 从本规划分支创建或使用功能分支，按 A–D 顺序实施，每阶段通过相关检查后本地提交；期间未完成的新模式不能伪装可用。
2. 将仓库任务配置显式升级为 schema 2 与 method，保留已有冒烟额度与历史说明；新增开发配置必须显式选择。记录升级步骤和旧任务预检错误示例。
3. 对旧 schema 1 回归、schema 2 回归/分类运行验证 inspect/reproduce/score 的兼容性，不改源文件；新运行使用 schema 3。
4. 完成软件验收后更新 `docs/modeling.md` 和新的开发验收记录；在 `overview.md` 中只更新实现状态，不以工程完成改写效果结论。同步本变更的主规格后再归档。
5. 回退使用先前代码与原镜像解释旧记录；新记录原样保留，由支持 schema 3 的代码读取，不将其降级冒充旧记录。无需迁移数据库或改写原始基准数据。
