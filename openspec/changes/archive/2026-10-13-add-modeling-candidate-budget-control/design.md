# Design

## Context

动机见 proposal.md。当前 `src/modeling/run.ts` 用 `Set<string>` 约束候选数量，分析请求有候选列表和优先级，训练动作带假设与证据，但没有可持续更新的候选实体。`Budget.childBudget()` 仅按固定配置和父剩余量分配额度；`eda.ts` 已能把结构化子额度交给完整双角色 `runAgent`，无需再造执行循环。

父记录已经保存动作载荷、实验和分析列表，`inspectModeling` 校验事件顺序及载荷哈希；交付和复现仍读取版本 1 的建模清单。现有测试覆盖有界失败、共享成本、两次独立 EDA 和完整交付，适合在同一实现上扩展。上一轮真实验收中，代码修复曾改用新的候选 ID，且验收器曾只检查第一条证据关联动作；本次应以稳定候选和实际实验身份检查关联，不能依赖候选名称猜测。

## Goals / Non-Goals

**Goals:**
- 在串行建模循环中维护一份有界状态，模型负责判断、宿主负责身份和事实。
- 一次工具动作同时表达候选决定与分析/训练/完成意图，校验和记录具有一致的接受边界。
- 为 EDA 暴露可申请的三项额度，复用现有预算与中止机制，保持实际消费可核对。

**Non-Goals:**
- 不增加独立管理角色、数据库、任务恢复/续跑、分支搜索或自动收益估计。
- 不用宿主语义分类器判定“两个想法是否等价”，不把优先级变成固定调度算法。
- 不改变训练的全局次数、每次超时、最终预留或数据划分，不引入按次训练额度申请。实验范围及研究边界见 proposal.md。

## Decisions

### 1. 候选清单与实验记录分开

在建模模块中增加独立的候选状态组件，以纯校验/状态归约逻辑配合现有串行循环，不建立通用工作流框架。候选上限沿用 `max_candidates`，统计任务内所有已创建身份，暂缓不会释放名额。

候选包含以下内容：

| 字段 | 归属与规则 |
| --- | --- |
| `id`、`hypothesis`、`change` | 模型创建；身份、核心假设与方向创建后固定，不静默覆盖 |
| `priority` | 模型更新的正整数，数值越小越优先；允许同优先级，摘要按优先级及创建顺序稳定展示 |
| `status` | 对外仅 `pending`、`tried`、`deferred`，对应待尝试、已尝试、暂缓 |
| `reason`、`evidence` | 模型的最近一次决定及依据；复用现有证据身份与适用范围校验，允许空证据并说明直接判断理由 |
| `experiment_ids` | 宿主在真实派发时关联，不能由模型填写；各实验单独保存完成、失败或未确认事实 |
| `revision` | 宿主递增的候选修改序号，用于关联动作、历史与快照；不增加并发编辑协议 |

模型只能申请暂缓或恢复；`pending/tried` 由宿主根据是否有实际尝试派生，防止模型伪造“已执行”。派发后的未知结果可以表现为已尝试，但必须同时显示实验未确认，不能据此宣称成功。暂缓后保留尝试列表，恢复时根据列表派生状态。

初始基线也是候选；最终全训练数据拟合继续关联所选候选，但以既有 `final` 标记区分，不混入搜索成绩。方向变化创建新 ID；同一方向的参数调整和代码修复使用原 ID，具体差异写入实验动作的改动说明。是否属于同一方向由模型解释，宿主只校验固定定义没有被覆盖。

不采用“成功/失败候选”状态，因为执行错误和一次成绩变差都不足以判断建模假设。三态之外的细节直接查询实验事实。

### 2. 更新附在原有三个动作上

升级建模提示词到新版本，三个工具均携带 `candidate_updates` 数组，允许为空；数组内使用明确区分的 `create`、`update` 操作。创建包含固定定义、优先级、理由及依据；更新仅允许优先级、暂缓/恢复、理由及依据，不提供覆盖固定定义的通道。每项更新引用一个候选，同一动作不得重复更新同一身份。

- `analyze` 用候选 ID 列表引用清单，保留问题、预期证据、决策规则与来源实验；创建的新候选可以在同一动作中被引用。派发给 EDA 的目标由宿主根据已接受候选解析为明确说明。
- `run_experiment` 引用候选，保留本次具体改动、理由、代码、来源实验及证据；不再让训练动作另外定义一套可以与候选冲突的核心假设。初始候选可以随首次训练创建。
- `finish_modeling` 仍选择当前可信最佳实验；可以附带暂缓其他方案的更新，不额外强制一次元数据工具调用。候选状态或优先级不改变最佳实验评分规则。
- 暂缓候选在再次分析或训练前必须先恢复，可附在同一动作中；不要求执行当前第一优先级候选，选择理由用于复核。
- 训练仍需满足当前对刚返回 EDA 的证据关联要求。候选更新引用证据不能替代训练动作本身的有效引用。

宿主每轮返回当前候选摘要与预算、最佳实验、当前动作反馈。摘要包括固定定义、优先级、状态、最近理由和证据身份、尝试数量及最近实验事实；全历史留在记录中，不反复注入代码或全部旧结果。沿用已有字符串、候选数、请求和轨迹字节上限，不进行隐式历史压缩或静默截断身份。

替代方案是增加独立 `update_candidates` 工具，但它会增加模型轮次并使“更新”和“执行”分离，首版不采用。

### 3. 明确实验修复关系和一致接受边界

训练动作新增可空的 `repair_of_experiment`。非空时必须指向当前任务、同一候选、非最终且已确认失败的实验。参数试验不冒充修复；未知执行不能自动重试。修复仍使用新实验 ID 并消耗既有训练/修复额度，不减免失败成本。

每个动作先在临时候选状态中解析更新，再校验候选引用、证据、修复关系、完成资格和可派发额度。预算预检必须无副作用；拒绝时不修改清单、消耗执行名额或生成子运行，但模型调用已发生的成本照常保存。

全部校验成功后，持久化包含候选变更与执行意图的一次接受记录，再应用状态并派发。沿用追加事件和记录故障停止规则；实际实验 ID、候选修订和修复来源在执行前关联。后续代码错误不撤销已接受的候选决定。持久化接受决定后中断时，检查可以识别已接受、待确认的执行，但本次不实现自动恢复。

不把逐项更新原清单后再校验当作原子接受；也不以模型已生成合法 JSON 作为可以执行的充分条件。

### 4. 每次 EDA 申请额度，宿主裁剪并告知

`analyze` 新增必填 `requested_budget`：`task_timeout_ms`、`total_tokens`、`executions`，以及非空的 `budget_reason`。三项均为正安全整数，缺失、零、负数、小数和未知字段在工具校验阶段拒绝，不默认填成配置上限。

分配原则：

```text
effective_time   = min(requested_time, configured_eda_time, remaining_time - final_reserve)
effective_tokens = min(requested_tokens, configured_eda_tokens, remaining_parent_tokens)
effective_steps  = min(requested_steps, remaining_total_eda_steps)
```

`eda_executions` 仍是整个父任务的 EDA 执行次数上限，不能在每次子调用恢复。模型尝试次数不是新增申请字段，继续取配置中的 `eda_model_attempts` 与父剩余尝试次数的较小值。调用次数也继续受 `eda_calls` 限制。任一必要维度无正额度则拒绝整个动作，反馈剩余额度和具体原因；超过上限但可以分配时透明裁剪，避免仅为额度修正浪费一次模型调用。

在派发意图中保存申请、实际额度、所有触发裁剪的约束及分配时父剩余快照；将实际额度交给完整双角色 EDA，并在结果反馈中一并返回。时间额度覆盖本次分析的输入准备、子运行和有界收尾，使用派发时的绝对截止时间，不能在准备完成或角色切换后重新计时。沿用中断和清理的有界宽限，不把清理时间说成免费额外探索时间。

token 仍为停止阈值：单个已派发响应可能超过阈值，必须记录全部真实消费并停止后续调用，不能截断账单或声称严格硬限额。分配不等于预付成本；串行子运行完成后只按实际消费结算。未知消费沿用全任务停止规则。到达已知子额度上限导致的 EDA 普通失败可以反馈给建模智能体，但不得作为成功证据或自动扩额再跑。

不让模型修改系统硬上限，也不申请训练额度；第一章规划/执行角色、工具和适中的任务粒度维持现状。

### 5. 版本化记录与兼容

保持父清单 `schema_version: 1` 及现有交付契约，增加独立带 `version: 1` 的 `candidate_control` 扩展，包含候选当前快照和所应用的事件位置。新动作载荷与预算事件由提示词/动作协议版本标识，检查时运行时校验；未知扩展版本拒绝按已知格式解释。

追加历史记录模型提出的改动、宿主接受结果、更新前后修订及关联实验；检查按已接受事件归约并对照快照和真实实验，核对修复关系、分配与子配置、结算身份，保留未确认子调用诊断。普通运行失败时也保存已有清单；记录故障不允许检查器补造缺失事实。

旧记录没有扩展时显示 `not_recorded`，继续按原规则读取和复现，不从旧候选名称或自然语言回填历史。现有任务配置继续可用，新的模型工具协议只用于新运行；更新测试夹具和验收器，不维护第二套旧决策循环。原生 EDA 清单不改变。

### 6. 验收与实现顺序

先完成可控模型的行为验证，再接真实 EDA：

1. 候选创建、排序、暂缓/恢复、同想法多实验、显式修复，以及非法批次不产生部分更新。
2. 两次 EDA 申请不同额度，第二次被父剩余额度裁剪；覆盖零额度拒绝、子阈值耗尽、未知消费、取消及幂等实际成本结算。使用假时钟或可控响应验证边界，不靠睡眠等待大额预算耗尽。
3. 合成数据的真实 Docker 整链：候选创建、完整双角色 EDA、证据关联更新、可控代码失败及同候选修复、保留可信最佳、最终交付与无模型预测复现。两次 EDA 的真实子配置必须与记录中的有效分配一致，不要求每次都耗完申请资源。
4. 检查旧记录兼容、篡改/不一致记录拒绝、原交付复现与隔离回归；运行 `bun run check`、相关 Docker 集成及严格 OpenSpec 校验。
5. 源码与配置提交后，独立入口在既有固定 `playground-series-s3e9` 开发任务上只运行一次真实模型有界验收。保持同一模型 profile、900 秒、40 次总模型尝试、600,000 token 阈值、3 次搜索拟合、1 次最终拟合、180 秒交付预留及现有 EDA 配置上限，不扩展正式任务集。实际模型须完成候选清单、一次明确额度申请的 EDA、依据证据的候选更新与后续训练、最终交付、无模型复现及冻结交付后离线评分；真实运行不强求随机出现代码错误或两次 EDA。

默认快速检查不调用付费 API。真实验收记录申请/实际/消费及完整失败，失败不自动加跑；若仅验收器有错误，可修复后对同一记录离线复核，保留原报告并独立保存复核结论，不覆盖为成功。不同额度、裁剪和修复的必达条件由可控测试保证，真实指标改善不作为通过条件。结果写入独立 `docs/modeling-candidate-budget-validation.md`，不改写上次验收历史。

## Risks / Trade-offs

- [候选清单增加上下文成本] → 限定候选数与字段长度，反馈当前摘要，完整变更留在记录；记录实际总成本，不预先声称节省 tokens。
- [同一想法的语义边界仍可能模糊] → 固定候选定义、显式实验改动与修复关系；宿主只保证结构和事实，不伪造语义判定。
- [模型申请过小导致 EDA 失败] → 真实反馈子额度耗尽，保留候选和成本，由建模智能体决定后续动作，不暗中抬高额度。
- [新增协议使旧模型动作不合法] → 新提示词明确展示字段和示例，更新所有可控响应与验收器，保留旧记录和任务配置兼容；不复用旧动作作为新运行的有效输入。
- [状态快照与执行事件漂移] → 一致接受记录、宿主生成实验关系、检查归约结果；记录失败立即停止，不用默认成功掩盖缺口。
- [一次开发运行被误作研究结论] → 功能验收只证明机制执行，候选选择和预算策略的收益留待后续独立实验。

## Migration Plan

按候选状态/协议、预算分配、循环与记录接入、整链验收分阶段本地提交。更新 `docs/modeling.md` 的动作与状态示例及兼容说明；保持已有数据准备、训练/预测入口和旧验收记录。合并前完成检查和本次有界验收。需要回滚时回退本次实现及配套提示词，新记录作为历史产物保留，不迁移或覆盖旧记录。

### 验收后的资源修正（2026-10-13）

用户在一次真实验收失败后明确要求按基准实际情况调整 16 MiB 产物限制。该失败模型（500 棵 ExtraTrees 与 HGB 集成）在同一允许训练数据上离线测得内部拟合 145.868 MiB、全量拟合 174.091 MiB。采用单产物 256 MiB、会话累计 1 GiB、工作区 512 MiB、内存 4 GiB、清理/中断宽限 15 秒；累计额覆盖执行与关闭各一次完整快照及元数据。更大任务继续显式配置，不把当前默认等同于全部基准资源协议。

配套修复整帧 base64 的线性校验和管道分片拼接，帧默认值为 `max(原帧默认值, 4*ceil(单产物字节/3)+64 KiB)`，显式冻结帧值不变。建模输入提供有效资源上限。此修正仅做无 LLM 容量验证，不改变一次真实模型验收已失败的结论，也不授权自动再跑；失败原因中 EDA 证据/预算问题独立保留。测量与验证见 `docs/modeling-resource-limits.md`。

### 任务 5.5 的证据与预算修复（2026-10-13）

用户随后暂停同步归档并要求先解决 5.5。原 EDA 第 4 单元因 `KeyError: 'age_bucket'` 失败，执行者仍引用其部分输出；校验拒绝正确，但提示词未明确可引用列表是唯一依据，纠错反馈也缺少具体 ID。保持成功单元/完整产物与规划者可见性规则，通过版本化提示词及结构化拒绝反馈纠正，不接受失败单元或自动改挂引用。

共享模型调用器将 profile 最大输出作为上限而非固定预留：实际 `max_tokens = min(profile 上限, token 阈值 - 已用量 - 输入字节估计)`。保留保守输入估计、请求/轨迹限额、真实消费和超阈值停止；事件记录 `remaining_budget_v1`、配置上限及实际请求值。执行者、规划者和建模调用共享同一实现，不通过增加子额度或修改冻结 profile 解决。

先以可控响应复现“成功单元→部分输出后失败→非法引用→无额外执行额度时纠正→规划者完成”，覆盖小于 profile 最大输出的总额度、合法列表与角色成本，再运行现有整链检查。本次用户要求修复并完成 5.5，允许修复提交后在原冻结任务和同一总预算下新增一次独立真实验收；保留首次失败报告，若仍失败不自动连续加跑。同步、归档和合并暂停。
