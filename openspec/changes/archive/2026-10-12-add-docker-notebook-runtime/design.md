# Design

## Context

动机见 [proposal.md](proposal.md)。仓库已有研究文档、数据下载器和校验器，没有应用代码、依赖声明、测试入口或正式 Spec。研究约束来自 `docs/overview.md` 第一章、`docs/benchmark.md` 的执行消融与评测隔离规则，以及 `benchmarks/README.md` 的数据访问边界。

已确认先在 macOS 本地开发，使用本地 Docker 的 Linux 容器完成任务隔离和集成验收；后续大量、耗时的实验再部署到 Linux 服务器。智能体通过代码单元工具操作内核，程序维护 Notebook。第一版使用合成数据与固定代码验证运行时。现有下载器及第三方资源保持原样。

## Goals / Non-Goals

**Goals:**

- 将控制、计算和记录分开，使执行接口不依赖模型供应商或 Benchmark。
- 明确每次执行是否开始、如何结束、状态是否仍可用，不在不确定时自动重试代码。
- 建立有界的资源、输出和生命周期行为，使失败也能留下可检查的记录。

**Non-Goals:**

- 不建立远程执行服务、Notebook 前端或多用户平台；控制程序连接本机 Docker 环境，本地开发使用 macOS，后续部署使用 Linux 服务器。
- 不实现模型调用、消融后端或任意历史轨迹的自动修复重放；具体产品范围见 proposal。
- 不将容器内桥接程序与生成代码之间的边界视为独立安全隔离；容器返回的内容一律视为外部输入。

## Decisions

### 1. 单仓库内分离控制层和执行层

建议目录为 `src/execution/`（协议、会话及 Docker 适配）、`src/records/`（宿主记录与产物）、`python/statigent_runtime/`（内核桥接、Notebook 校验与重放支持）、`docker/`（执行镜像）、`tests/`（快速测试与独立集成测试）。不拆包、不建立服务。

Bun + TypeScript 使用 strict、ESM、Biome 和运行时消息校验；Python 使用 uv、Ruff、pytest。实施时选择并固定兼容版本，提交 `bun.lock`、`uv.lock`、运行时版本声明和镜像构建配置。版本确认属于工程落地，不预先承诺未验证的版本组合。

默认 `bun run check` 汇总非写入式格式/lint、类型检查和快速测试；提供 `format`、`lint`、`typecheck`、`test`。Python 检查全部经 uv；Docker 测试通过独立 `test:integration` 入口启动，不在默认检查中拉镜像、下载数据或调用模型。现有下载脚本不纳入无关批量格式调整。

备选是先做纯 Python 运行器；它会推迟验证已确定的 TypeScript/Python 边界，因此本次直接打通跨语言链路。

控制层使用可在 macOS 和 Linux 上工作的进程与文件接口，通过 Docker CLI 管理容器，不依赖宿主 `/proc`、Linux 专有命令或写死的 Docker socket 路径。输入暂存目录、运行产物根、镜像和资源配额均配置化；镜像构建上下文仅包含运行时源码与依赖声明，不带入基准或宿主配置。

本次优先构建和验收本机原生架构对应的 Linux 镜像，不要求同时构建所有平台。若本机与未来服务器架构不同，沿用 Dockerfile 和锁文件分别构建验证，记录各自的镜像身份；不假设 arm64 与 amd64 镜像具有相同 digest。跨架构模拟结果不用于正式性能对比。本次的同条件重放仍使用原运行的相同镜像和平台；跨平台迁移冒烟测试属于独立运行。

### 2. 每个会话一个容器、一个真实内核

由宿主 TypeScript 管理容器，在容器内使用 Python 桥接程序与 `jupyter_client`、`ipykernel` 管理真实内核，以 `nbformat` 校验标准 Notebook。预装 NumPy、pandas、Matplotlib，满足合成 CSV、跨单元计算和静态图表验收；本次不预装完整建模库栈。

采用 Jupyter 内核可复用输出和执行协议，避免自行用 `exec()` 模拟 Notebook。首版不启动 Jupyter Server；桥接程序和内核只在容器内部通信，不开放宿主端口。Python 桥接、内核启动命令及重放工具均经 uv，运行时离线使用镜像中已安装的锁定依赖，不临时同步或安装依赖。

Jupyter 消息使用父请求标识关联输出，内核重启产生新的状态身份；具体遵循 [Jupyter 消息协议](https://jupyter-client.readthedocs.io/en/stable/messaging.html)。本项目另外维护宿主生成的 `kernel_epoch`，避免重启前后的状态混淆。

### 3. 宿主通过标准输入输出传递有版本的 JSONL 消息

首版使用无 TTY 的 Docker 子进程管道连接桥接程序。stdout 专用于结构化协议，桥接诊断写 stderr；用户代码的 stdout/stderr 从内核消息中收集。相较 HTTP 服务，该方式无需容器网络、监听端口或额外认证服务。

消息携带 `protocol_version`、`request_id`、`session_id`，执行消息再携带 `cell_id`、`kernel_epoch` 和实际调度序号。控制程序公开会话创建、执行、取消、显式重启、关闭接口；未来智能体的代码工具只需提供代码，关联 ID 和上限由控制层注入。

请求与返回均做运行时校验，消息字节数和字段长度有上限。执行完成结果区分 `ok`、`error`、`timed_out`、`cancelled`、`kernel_lost`、`output_limit_exceeded`、`protocol_error`；未执行的拒绝或排队取消明确标记 `started=false`。结果附带耗时、输出预览、产物引用、异常和内核可用性。配置/协议错误不会触发代码重试。

同一请求 ID 的重复提交被拒绝，不造成再次执行；断开连接后无法确认是否执行的请求记录为结果未知，并使会话失效，不承诺跨进程 exactly-once。每次主动修复或重跑必须产生新的请求和单元 ID。

### 4. 生命周期由宿主控制，执行与取消分开处理

会话状态为 `starting`、`ready`、`busy`、`interrupting`、`restarting`、`failed`、`closing`、`closed`。同一会话按接收顺序排队执行，队列有容量上限；取消和关闭走独立控制路径，不等待长时间运行的代码退出后才处理。

- 启动有截止时间；缺少 Docker、镜像或所需限制能力时明确失败，不退回宿主 Python 执行。
- 普通 Python 异常保留已发生的变量和文件修改；若确认内核可用，返回 ready。程序不自动回滚数据，也不自动修复代码。
- 执行超时或取消时先中断；在宽限期内确认执行停止并且内核可用后才能继续。对正在执行的代码，已发生的部分修改可能仍存在。
- 无法确认停止、桥接协议损坏、内核退出或容器 OOM 时，将会话标为 failed，并终止容器中的进程。宿主超时监控独立于桥接程序。
- 显式重启创建新的内核 epoch、取消旧队列，不恢复内存变量；若容器仍健在，可保留任务工作文件，并明确返回保留情况。失去容器后不假装文件仍然存在。
- 关闭是幂等操作；阻止新请求、取消排队任务、处理活动执行、尽力收集可用产物，最终清理容器。控制程序异常退出可能留下容器，按运行 ID 标签提供仅清理本项目指定运行的入口，不清理无关容器。

在会话配置中明确启动、单元、任务总时限、中断宽限、CPU、内存、进程数、队列长度、输出与工作空间上限；无正数有效上限时拒绝启动。达到任务总时限后停止接收新执行并关闭会话。具体默认数值由小型合成冒烟测试确定并写入配置及说明。

### 5. 容器只获得任务必需的权限和数据

输入由可信调用者显式提供文件清单，复制到当前运行的独立暂存目录；拒绝越界路径、符号链接及非普通输入文件，随后只读挂载为 `/input`。不直接挂载整个仓库、数据根目录或包含答案的目录。第一阶段不判断任意输入内容是否含答案，基准输入筛选由后续可信适配器负责。

容器以非 root 用户运行，根文件系统只读，移除不必要 capabilities，开启 no-new-privileges，保留默认 seccomp；无特权模式、宿主网络、宿主 PID 空间、设备或 Docker socket。环境变量采用白名单，不继承宿主密钥。Docker 默认不限制资源，因此必须显式设置 CPU、内存、swap 策略和进程数。[Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)、[Docker 运行参数](https://docs.docker.com/engine/containers/run/)

`/workspace`、临时目录和 Jupyter 运行目录使用有容量限制的任务私有可写空间；首版可用受限 tmpfs，避免任意写文件填满宿主磁盘。其内存占用计入任务限制，这是第一阶段小型验收的取舍；未来大规模数据和建模需要另行设计磁盘配额。

每个单元结束后，桥接程序枚举工作目录中限额内的普通文件并传送产物；宿主独立校验大小、路径和 MIME 元数据，生成自身产物 ID，保存快照和校验值。拒绝符号链接、特殊文件、绝对路径和路径穿越，不执行产物。容器不能访问宿主记录目录；图表等 MIME 输出也由协议传送并在宿主保存。关闭前再收集一次，若容器已被杀死，仅承诺保留已接收的记录与产物，并报告未收集部分可能丢失。

### 6. 有限结果反馈与完整度标记

记录 `stream`、`execute_result`、`display_data` 和 `error` 输出；支持静态 PNG 图表及文本/HTML 表格数据，不提供交互式 widget 或执行 HTML 的界面。处理显示更新与清屏，或明确保留为带类型事件，不能把不同单元的输出混合。禁止交互 stdin，避免代码等待用户输入而悬挂。

工具反馈采用有大小限制的预览和宿主产物引用，完整输出在配置的保存上限内落盘。预览截断与保存截断分开标记；超过总输出/产物限额时停止收集并中断当前执行，返回明确的限额结果，保留已收集内容。不能把被丢弃的数据称为完整保存。

单元完成需匹配执行回复与执行结束状态，不能仅以第一条输出或 shell 回复作为全部输出已收集的依据。迟到输出必须按原请求归属记录，未知来源输出记为诊断，不归到下一个单元。

### 7. 宿主记录事实，Notebook 是记录的导出视图

每次运行在忽略 Git 的独立目录保存 `manifest.json`、`events.jsonl`、`notebooks/` 和 `artifacts/`。运行清单记录唯一 run ID、时间、commit/dirty 状态、完整非敏感配置、输入校验值、镜像 ID/digest、宿主操作系统与架构、Docker Engine 版本、实际容器平台、依赖与运行时版本、种子及可获取的硬件信息。无模型、提示词、token、划分时标为不适用，不伪造已测量值。本地功能验收与服务器正式实验分别记录，不能混合环境耗时后声称方法性能差异。

宿主在派发前写入执行开始记录，收到输出时追加事件，结束时记录终态和耗时；异常退出留下的未完成执行标为 interrupted/unknown。已执行代码、失败尝试和旧输出不可被后续修复覆盖。记录持久化失败时停止新执行并使运行失败，不能继续产生不可追溯结果。

每个 kernel epoch 生成独立 `.ipynb`，按实际执行顺序追加代码单元、执行计数、输出及元数据。重跑同一段代码是新尝试；错误单元仍保留。Notebook 格式和 MIME 输出遵循 [nbformat 文档](https://nbformat.readthedocs.io/en/stable/format_description.html)，导出时校验；原始事件日志保留清屏前和显示更新前的轨迹。

重放创建全新容器、空工作空间和独立 run ID，复用相同输入、镜像、种子和配置，按单元顺序运行，不读取原会话中间文件；保存 replay-of 关联和独立结果，不覆盖原输出。原 Notebook 含错误、保存内容截断、中断或跨 epoch 依赖时，首版返回不支持验证及原因，不擅自删除单元或声称复现通过。仅工具预览截断且保存内容完整不影响资格。正常流程中任一单元失败则重放失败；全部执行成功只证明可执行重放，数值正确性另外由合成夹具的已知结果断言，图表只检查可解析与存在，不要求 PNG 字节完全一致。

## Risks / Trade-offs

- [容器隔离依赖正确配置及底层 Linux 内核] → 在本地 Docker Linux 容器中真实检查挂载、网络、权限和资源；迁移服务器后复验，不将其描述为可防御任意宿主漏洞的沙箱。
- [中断不一定终止用户生成的所有后台活动] → 不支持跨单元后台作业；无法确认执行收敛时终止容器，禁止未确认的会话继续运行。
- [桥接层与生成代码同属任务容器，数据可能被伪造] → 宿主限制协议与文件访问，记录容器生命周期事实；分析结果真实性由后续独立评分和证据检查验证。
- [tmpfs 不适合较大分析产物] → 本次明确限定合成数据验收，配额写入清单；正式基准接入前单独验证存储策略。
- [错误轨迹导出不等于可从头重放] → 分别记录导出、重放资格和重放结果；自动整理失败历史不纳入本次。
- [宿主平台、处理器架构及 Docker 配置差异] → 当前在本地 Docker 完成真实集成测试，快速检查不能替代容器测试；记录实际平台及限制配置，后续服务器部署时重跑同一入口。本地验收通过不表示服务器性能或长期稳定性已验证，但服务器验证不阻塞本变更完成。

## Migration Plan

这是新增运行时，无旧接口或数据迁移。先完成工程与协议快速测试，再在本地 Docker 构建固定 Linux 镜像，运行真实内核和隔离测试，最后执行合成 CSV 的完整验收与独立重放，记录实际验证环境。使用说明给出本地构建、运行、验证、产物位置和指定运行清理命令。全部当前集成验收可在本地完成，不要求先获得 Linux 服务器。

后续开始大规模实验时，将相同控制程序、Dockerfile 和锁定依赖部署到 Linux 服务器，按目标架构构建镜像并调整路径及资源配置；重跑集成测试、小规模冒烟测试，再验证并发和长时间稳定性。正式耗时与资源比较在固定服务器环境下进行。这些步骤作为后续部署工作，不计入本变更的实施完成条件。

回滚时停止新会话并关闭本次运行的容器，保留已导出的记录；镜像可按配置切回旧版本。任何清理只针对显式运行 ID，不删除原始基准或其他实验记录。本次不执行真实模型调用及正式 Benchmark。
