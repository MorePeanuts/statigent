# Proposal

## Why

第一章需要在有状态的 Notebook 中开展多步分析，并将执行过程、证据和开销保存为可复核产物；当前仓库只有研究文档与基准数据准备工具，尚无执行运行时。先建立基于 Docker Linux 容器的持久执行底座，在本地完成开发和集成验收，可以在不调用模型的条件下验证状态保持、隔离、故障处理和重放，为后续 EDA 智能体及消融提供共同基础。

## What Changes

- 建立 Bun + TypeScript 控制层及 uv 管理的 Python 工程基础，固定依赖与开发工具，提供快速检查和独立 Docker 集成测试入口。
- 为每个任务创建独立 Docker 容器，在容器中维护持久 Python 内核；控制层负责启动、串行调度、中断、显式重启和清理。
- 提供执行代码单元的结构化接口，返回文本、结果、图表引用、错误、耗时及内核状态；拒绝无效消息，限制输出和资源消耗。
- 仅暴露任务允许的只读输入及独立工作目录，隔离宿主凭据、评测材料、其他任务与外部网络。
- 在容器外保存运行清单、追加式执行轨迹、产物索引和自动生成的 Notebook；支持在新会话中重放正常多步分析，并独立报告重放结果。
- 使用小型合成 CSV 和固定代码验收，不调用付费 API、不运行正式基准。

本次不实现模型供应商接入、单智能体或规划—执行循环、Benchmark 适配与评分、每轮新脚本消融、预测建模、Notebook 网页界面、GPU 或分布式调度。执行接口为后续复用保留边界，但不预建这些功能。

## Capabilities

### New Capabilities

- `execution-session`: Docker 任务会话的隔离、资源约束、生命周期、串行调度、超时、取消与状态丢失语义。
- `notebook-execution`: 有状态代码单元的结构化执行协议、输出和错误反馈、消息关联及结果容量限制。
- `execution-records`: 运行清单、不可覆盖的执行尝试记录、产物引用、Notebook 导出与独立重放结果。

### Modified Capabilities

无。当前尚无正式能力规范。

## Impact

- 预计新增 `src/` 下的执行协议、会话管理与记录模块，`python/` 下的内核桥接与 Notebook 支持，`docker/` 下的执行镜像及合成测试夹具；具体组织见 design。
- 引入真实 Python 内核及 Notebook 格式支持，服务于跨单元状态与标准产物；所有 Python 启动和检查经 uv 执行。
- 本次支持在 macOS 本地通过 Docker 运行 Linux 容器并完成集成验收，保留以后部署到 Linux 服务器的能力。普通开发检查不依赖 Docker；未具备 Docker 时不能报告集成验收通过。服务器部署、并发及长时间运行验证留到后续实验阶段，不作为本变更完成的前提。
- 新增根目录开发入口、锁文件、运行产物忽略规则及执行环境使用说明；不改动原始基准、上游代码或研究方法定义。
- 第一阶段只记录实际执行时间与资源配置。模型、提示词和 token 成本标为不适用，不宣称已具备智能体成本评测能力。
